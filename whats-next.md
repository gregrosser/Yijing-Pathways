This was the largest single thread of the session. Sequence of reports and fixes, each **verified** at the time but each later found insufficient for the next report:

**Round B — "FX{45,46,53,54}/KW{21,22,47,48} doesn't display as intended"** (this exact group/report recurred **four times** across the rest of the session, each time after a fix that turned out incomplete):

- *Sub-fix 1*: found and fixed a real, generalizable bug — `drawDistanceBracket()`'s label circle/rect has a **fixed** visual size, and when a group's own badges span a short vertical distance (many groups, not just this one), the label was as big as or bigger than the gap between its tick marks, visually swallowing them. Widened the margin (16→80px total, guaranteeing ≥40px clearance) — reverified.
- *Sub-fix 3 (the deep one)*: user reported "still not one zoom level renders as intended" — this led to discovering the **actual root architectural bug**: `.fx-spine-frame`/`.kw-spine-frame` had a **fixed** `140px` gutter padding, but the two panels' grid-column widths (`1fr` / `0.825962fr`) were tuned to make the FX and KW spine SVGs render at **matching heights** despite different aspect ratios — and subtracting the *same fixed* 140px from two *different-sized* columns breaks that ratio, increasingly so as the viewport narrows (proven both algebraically and by direct measurement: at 800px viewport the two spine heights already differed, and the divergence grew with narrower viewports). **Fixed** by changing both paddings to a **shared percentage** (`20%` instead of `140px` — proven algebraically that any *shared* percentage preserves the original height-matching ratio, unlike a shared fixed px amount) — verified the height ratio is `1.0000` from 800px to 3840px viewport widths. Also made the distance-label's radius/font-size/margins scale with the diagrams' own rendered size (via `svg.getBoundingClientRect().height / REFERENCE_SVG_HEIGHT`) instead of using fixed px, so the bracket stays correctly proportioned at any scale. Verified with a 100-combination sweep (5 viewport widths × 20 groups) — zero problems.
- *Sub-fix 4 — the real Firefox diagnosis*: despite sub-fix 3 passing every automated check, the user's actual screenshots (in Firefox, confirmed via `navigator.userAgent` from a console dump they ran) kept showing the exact same visual gap. ## Positioning/scaling architecture of `diagrams/FX_KW_spine.html` as it stands now (for anyone editing this file next)

- `--page-w: min(4056px, 100%)` and `grid-template-columns: 1fr auto 0.825962fr` (in `.page-columns`) together make the FX and KW spine panels render at **matching heights** despite their different native aspect ratios (FX viewBox `348×661`, KW viewBox `287×660`) — the `0.825962` fraction is derived from the ratio of the two viewBoxes' aspect ratios and is load-bearing; don't change it without re-deriving.
- `.fx-spine-frame`/`.kw-spine-frame`'s gutter padding is `20%` (a **shared percentage**, not a fixed px value) specifically because a shared percentage preserves the above height-matching ratio at any viewport width, while a shared *fixed-px* padding (the original design, `140px`, before this session's Round-B sub-fix 3) does not, and increasingly breaks it as the viewport narrows. **Do not revert this to a fixed-px value** without re-deriving the height-matching math (laid out in full in `<work_completed>` §11 sub-fix 3) — this was a genuine, algebraically-proven bug fix, not a stylistic choice.
- The spine-side distance bracket (`drawDistanceBracket()` in the `<script>`) scales its label radius/font-size/margins via `scale = svg.getBoundingClientRect().height / REFERENCE_SVG_HEIGHT` (currently `REFERENCE_SVG_HEIGHT = 1024.40625`, measured at a 1920px-wide Chromium viewport — this is a *reference* value the scale factor is relative to, not a hard constraint; it can be re-measured/adjusted if the diagram's baseline size ever changes intentionally). Both the spine-side bracket (`.distance-bracket-line`/`.distance-tick`) and the newer under-box bracket (`.hd-distance-bracket-line`/`.hd-distance-tick`) are drawn as **filled `<rect>` elements, not stroked `<line>` elements** — this is deliberate (see the Firefox findings above), don't "simplify" back to `<line>` elements without re-reading why.
- `positionHexDisplays()` and `drawDistanceBracket()`/`renderHdDistanceBracket()` are all called from a single `update()` function, itself called on initial page load and on every `pageshow` event (bfcache-safety, an established pattern from before this session) — but **not** on `resize`. The `resize` listener only calls `positionHexDisplays()` (repositioning the boxes if a group is active), not full `update()` — meaning the spine-side distance bracket's coordinates are **not** recomputed on a bare `resize` event. This was investigated as a possible explanation for the Firefox bug (real Firefox zoom fires `resize`) but a headless simulation of "load once, then resize without reload" showed the bracket's *relative* internal geometry (line-to-label gap) stays self-consistent even without recomputation, since nothing in it depends on absolute viewport position — so this was **ruled out** as the cause of the Firefox bug, but the underlying fact (resize doesn't trigger a full bracket recompute) remains true and could matter for some *other* future symptom (e.g. if the gutter fraction or REFERENCE_SVG_HEIGHT-relative scale ever needs to react live to a mid-session resize without a full reload).
